# 技术架构

v0.2.0 / 2026-10-19。

## 技术选型

| 方案 | 本项目匹配点 | 首版成本与取舍 | 决定 |
| --- | --- | --- | --- |
| Phaser | 完整游戏框架，场景/输入/资源/物理生态；官方支持移动与桌面网页 | 当前无物理、多关卡需求，需引入框架和生命周期；并非本项目已实测性能较差 | 后续多场景版候选 |
| PixiJS 8 | 场景图、精灵、GPU 渲染与特效，适合大量美术资源 | 规则、状态、随机和平衡测试仍需自建；当前对象少，GPU 能力并非首版必要条件 | 后续美术升级候选 |
| 原生 Canvas 2D + DOM | 已足够画闭环轨道、少量寿司与动画；无运行依赖，易导出单文件 | 命中测试、适配、生命周期需自行写；应避免发展成自制大型引擎 | **首版采用** |

依据链接见 RESEARCH.md。这是按当前范围做出的工程判断，未进行三种引擎的性能基准或包体对测，不能宣称原生 Canvas 普遍优于其他方案。

## 模块

```text
index.html + style.css     原生 DOM 按钮、HUD、角色卡与弹窗
           ↓
src/main.js               输入映射 / 固定步长 / 暂停 / 声音 / 对局日志
       ↙          ↘
src/core.js         src/renderer.js
纯逻辑和带种子随机   Canvas 绘图、轨道布局、命中区域、短期效果
       ↑
tests/core.test.mjs + scripts/simulate.mjs
tests/browser/game.spec.js → 实际 Chrome 页面与触屏模拟
```

- **Game** 只接受时间推进、进食、开始、暂停、继续；不依赖浏览器或 DOM。
- 逻辑 60 Hz；`step()` 支持小于 1 秒的外部步长并拆成最大 1/60 秒；单次超 1 秒截断，调用方应按小步推进。应用层超过 0.5 秒无帧主动暂停。
- `Renderer` 用 CSS 像素坐标，绘制缓冲区乘以 min(DPR,2)。触屏与鼠标位置都减画布边界，不依赖页面滚动偏移猜坐标。
- 闭环轨道以周长比例存储盘子位置，窗口旋转只重排布局，角色数值与食物进度保持不变。
- 绘图顺序按 y 排序；命中重叠时取最近中心。可点击半径移动端至少 28 CSS px；入口要求周长 8% 的净空，避免密集遮挡。
- 最多 14 个盘子、32 个规则事件；粒子短时自动移除。纯规则层不发网络请求；联网由 social.js、API 和数据库分层处理。
- `visibilitychange`、`blur`、帮助弹窗均进入暂停；不自动恢复，防止玩家尚未准备就失血。
- 本机保存最高分、声音开关、玩家 ID、随机设备凭证与最多 3 份待提交记录。localStorage 拒绝访问时降级为内存模式；联网局发送进食时刻/盘 ID 日志用于积分复算。
- 正常访问不暴露测试接口；`?test=1` 显式启用 `window.__sushi`，供本机自动测试设置确定性局面。测试接口创建的合成游戏为练习局，不能直接写入共享榜；联网成绩由服务器复算，仍不承诺专业竞技级防作弊。

## 构建与运行

客户端无第三方库依赖；Node 24 开发服务器同时提供静态文件、本地 API 和内置 SQLite，数据库保存在 .data/local.sqlite。默认绑定 127.0.0.1，用户指定 `--host` 才绑定 0.0.0.0。拒绝路径越界、隐藏目录及 node_modules。

`scripts/build.mjs` 复制静态文件并将本项目四个模块按依赖顺序合并成 `play.html`，内联样式与图标。它是此工程的简单专用构建脚本，不是通用 JavaScript 打包器。未来引入复杂 import、资源管线或 TypeScript 时，应改用 Vite 等标准构建方案。

开发依赖为 `@playwright/test@1.64.1`、`drizzle-kit@0.31.10`、`drizzle-orm@0.45.2`，由 package-lock.json 锁定。规则测试使用 Node 自带 test/assert。

## 扩展原则

先保留 `Game` 输入/输出契约，再替换渲染层或加原生容器。后续独立拆出食物/角色数据表、音频、场景管理和存档迁移。共享排行榜已按用户请求在 v0.2.0 实现。支付、完整账号与广告仍未实现。


## v0.2.0 联网层

src/social.js → Worker API → D1。GitHub Pages 与 Sites 前端连接同一公开 API；localhost 使用本地 API 和独立 SQLite，不污染公网榜。file:// 始终为离线练习。采用 X-Player-Key 跨源请求，不依赖第三方 Cookie；服务器只保存凭证的 SHA-256，榜单不返回凭证或操作日志。

API：POST /api/runs 认领 ID 并创建服务端随机种子；POST /api/runs/:id/finish 提交活动 ticks 与成功进食日志；GET /api/leaderboard 返回前 50 名和本人名次。服务端使用同一纯规则 Game 按 60 Hz 重放，独立算出积分、寿司盘数和死局，检查所有权、真实经过时间及操作合法性，不接受客户端自报总分。重复结算幂等，SQLite/D1 事务保存个人最佳。

Drizzle 声明模型及生成 SQL 在 db/、drizzle/ 版本化管理。迁移在部署/本地服务器启动时应用，不在请求中执行 DDL。托管清单声明 D1 绑定 DB；构建脚本在该配置存在时额外生成自包含 Worker ESM 和 dist/.openai/drizzle。原离线/静态构建继续保留。

输入限制：每个凭证每分钟最多 8 次开局；提交最大 1 MB、25,000 次进食、6 小时活动 ticks，7 天有效。这些用于原型资源保护，不改变客户端游戏数值。没有统一 IP 反滥用配额、验证码或专业机器人检测；长期/恶意流量下的资源上限仍需观测。客户端保存最多 3 份失败提交，刷新榜单时重试。

ID 是轻量浏览器身份。不同域名/设备存储隔离，不能仅靠 ID 取回所有权，没有密码找回。服务连接失败时练习局仍可运行，不伪称已上榜。数据库保存玩家 ID、成绩和验证对局记录；尚未设置自动数据保留清理。
